# Desktop port-forward contract

`agent-remote --desktop-control` exposes four device-scoped methods:

- `port_forwards.list` reads the safe projection for the active device.
- `port_forwards.create` accepts a reviewed session/node/backend and port/TTL intent. Rust reserves the caller key before the Server request and reuses it for the bounded transport retry. An empty key is generated by Rust.
- `port_forwards.stop` stops the exact forward after rechecking its device, session and node binding.
- `port_forwards.reconnect` explicitly requests a fresh short-lived connection authorization for an existing non-terminal forward.

The human `forward` command also accepts the global `--json` flag. In start
mode it emits one `port_forward_started` event only after the local
`127.0.0.1` listener has been bound. The event contains the safe forward
projection, local port, listener state and an initial remote-readiness
snapshot; it never contains
the one-time connection token or SSH details. The process remains attached to
the listener and owns the bounded reconnect loop until interrupted. Desktop
uses this event to supervise a real listener instead of treating a control
plane create receipt as proof that a port is listening.

The response projection omits user/device identifiers and one-shot connection tokens. A transport failure returns an unknown outcome; the desktop must retain the original caller key and query or refresh explicitly. It must not submit a new key or infer the latest forward.

## Exact listener recovery

After a desktop process restart, the UI starts the hidden human command with
`forward --forward-id <full-uuid> --local-port <port>`. This mode lists the
exact UUID bound to the current device, verifies its session/node context, binds
the local loopback listener, and then calls the single-use connection endpoint.
It never calls the session port-forward create endpoint and therefore cannot
create a duplicate forward. The connection response may include only the
non-secret Node routing fields (`node_wireguard_ip`, `ssh_user`, `ssh_port`)
needed to rebuild the SSH tunnel; the token remains in the Rust process and is
never emitted in the startup event, desktop-control receipt, argv, or journal.
Servers that do not provide these routing fields fail closed with an upgrade
message rather than falling back to a new forward.
